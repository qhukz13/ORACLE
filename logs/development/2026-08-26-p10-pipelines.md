# Phase 10 — pipelines, and four things the spec could not have known

**Task:** P10-T1…T6 · **Date:** 2026-08-26 · **Status:** built, green

PIPELINES.md was written before the task graph existed and revised once by the 2026-08-24 replan.
Building it turned up four places where the document and the code could not both be right. All
four are corrected in the document rather than worked around in the code, because a spec that
disagrees with its implementation is worse than no spec — the next reader cannot tell which half
to trust.

---

## 1. The P7 defect this phase uncovered

`Limits.timeout_s[TaskKind.TOOL]` is **120 s**. `dev.run_tests` declares `TEST_TIMEOUT_S + 30 =
630 s` in its own contract and `dev.build` declares **930 s**.

So **any TOOL task in any graph running either tool was killed by the scheduler at two minutes**,
and the status it got was `TIMEOUT` — which reads as *the tests hung*, not *the scheduler did not
wait*. It has been true since P7-T2 and nothing failed loudly enough to find it: graphs so far ran
delegations (3600 s) and verifications (900 s), and the one kind whose default is short is the one
a pipeline is made almost entirely of.

`Task.timeout_s` (migration `0004`) is the fix, and it is not a pipeline feature —
ORCHESTRATION.md §3 already specifies the layering *tool contract < step < task < graph*, and this
is the level that was specified and never built. It is the only change Phase 10 made below the
pipeline layer, and it should not be reverted if pipelines ever are.

`TestTaskTimeoutOverridesTheKindDefault` pins it in both directions, including that a task with no
ceiling still gets the kind default, so the override cannot quietly become "no timeout".

## 2. The spec contradicted itself, twice

**`on_failure: ask`.** §3 offers it — *"pause and ask; converts the run to `waiting`"* — nine lines
after saying *"Approval is up front, once … never a prompt mid-run."* Both cannot hold. The
security model breaks the tie: `ask` is refused at validation, by not existing in the enum. And
`waiting` has since acquired a meaning — `TaskStatus.WAITING`, "scheduled but parked" — so the
sentence would now also be describing a per-task state as if it were a run state.

**`retry: { on: ["timeout"] }`.** §2's example uses it; §3 says twenty lines later that retries
apply *"only to steps declared retryable in their tool contract — the tool decides, not the
pipeline author"*. The example picks the losing side of its own document. `retry: { max: N }`
survives and sets `Task.max_attempts`; which failures earn an attempt stays with
`runners/tool.py::RETRYABLE_KINDS`.

## 3. Three things in the worked example do not exist

§2's `asterim-check` example — the one a reader would copy — names:

* **`with: { project: "{{ project }}" }`**. No tool takes a `project` argument; `git.status`,
  `dev.run_tests`, `dev.build` and `dev.execute` all take a `ScopedPath`. And `{{ project }}` was
  ambiguous in a way that only shows up when you try to use it: the file header's `project:` is a
  **name**, every tool argument needs a **path**. Split into `{{ project.name }}` and
  `{{ project.root }}`.
* **`tool: oracle.report`**. Not registered, not planned. And structurally impossible as a *step*:
  a step downstream of a failure is `SKIPPED` by `_cascade_skips()`, so a reporting step could
  never report on a failed run — the only run whose report anybody wants. The run record is written
  by `PipelineService` from the task rows after the scheduler returns.
* **`capture: junit`**. `dev.run_tests` parses results in-process and writes a text blob; there is
  no junit file on disk.

`test_the_two_shipped_pipelines_are_real` is the guard against this recurring: it prices both
shipped files against the **real** `config/policy.yaml` and the **real** tool registry, so a
renamed tool or an argument a contract does not take fails a test rather than a run.

## 4. A policy entry that is a floor, not a price

PIPELINES.md §3 says `tier(pipeline) = max(tier(step) for step in steps)`. The first implementation
put `pipe.run: { tier: T2 }` in `config/policy.yaml`, beside `ai.graph`, which reads correctly and
is wrong: **`evaluate()` raises a tool's tier to its `declared_tier` and never lowers it**, so a
policy entry is a floor. With T2 as the floor, a pipeline of nothing but reads still asked, and the
max rule was unimplementable.

Found by a test — a read-only pipeline hung for 180 s and came back `refused`, which is an approval
nobody answered. `pipe.run` is now **T0**, with a comment in `policy.yaml` explaining that the entry
exists to make the pseudo-tool *known* (`default_decision: deny` means an absent one is refused),
not to say what it costs. A run containing a T2 step is priced T2 and asks; a run of reads asks
nobody. `test_the_shipped_policy_still_says_this` asserts the real file, so the test policy and the
shipped one cannot drift apart — which is the failure mode that produced four of the five
instrument defects this project found in its first week.

## What the shape ended up being

**Every step is one `Task(kind=TOOL)`.** No new `TaskKind`, no new runner, no `pipeline_runs`
table, and exactly two new event types — `pipeline.started` / `pipeline.finished` — neither of them
a `task.*`. The steps emit ordinary task events because they *are* ordinary tasks, so `TaskTree`
renders a run with no new code.

The roadmap's extra criterion is a test rather than a claim:
`test_the_two_produce_the_same_events_in_the_same_order` runs a compiled pipeline and a
hand-written graph of the same steps through the scheduler and compares the normalised event
sequences element for element, then asserts no event type is unique to either.

**`on_failure` is edge construction, not a runtime concept.** `abort` makes a step the barrier the
next one waits on; `continue` makes it a leaf nothing depends on, so its failure cascades to
nothing. That leaves one visible consequence, accepted deliberately: **a `continue` step and its
successor may run concurrently.** The alternative is a completion-only edge in `graph.ready()`,
which means touching the fail-closed rule (`all deps SUCCEEDED`) that the whole graph algebra rests
on. That is a P7-core change and not one to make on speculation about a pipeline nobody has written.

**`when: false` omits a step rather than compiling it `SKIPPED`.** `SKIPPED` means *an ancestor
failed and this never ran*; reusing it for *the author's condition was false* would put a lie in
the one field the UI reads to explain a run. Omitted steps are reported separately and shown on the
card, because a run is defined as much by what a parameter removed as by what is left.

## The grants, which are the dangerous part

One card authorising six actions and one card nobody reads are the same gesture. Five structural
constraints, each a security test, and six of the 21 cases in
`tests/security/test_pipeline_authority.py` are about this one function:

1. the card lists every elevated step with its **resolved** arguments — not a count;
2. each grant binds to the digest `preview()` computed from those resolved arguments, and
   `execute()` recomputes it, so a mutated argument fails with a valid id in hand;
3. single use, and per task — two identical steps get two grants;
4. **T3 never reaches a card**: refused at validation, because a T3 needs a phrase typed for *that
   invocation* and batching one would launder `confirm_strong` into `confirm`;
5. revoked in a `finally`, whatever ended the run.

And one about provenance rather than content: a pipeline under `<project>/.oracle/pipelines/` is
**repository content**, the same trust class as a checked-in `AGENTS.md`, so it carries
`local_foreign`, the gate escalates it, and the loader pins its `project` so a cloned repo cannot
ship a workflow that acts on a different one. The card says which source a pipeline came from,
because the tier alone does not.

## The evaluator

PIPELINES.md's one hard promise about this code is *"never `eval`"*. `ast.literal_eval` is not the
cheap way out either — it is safe about *values* and says nothing about the expression around them,
and reaching for it is how a "safe evaluator" acquires attribute access. So `template.py` is a
whitelist tokeniser and a ~90-line recursive-descent parser over `or · and · not · ( ) · == · != ·
true · false · string · int · ref`, depth-capped at 8 because a recursive-descent parser handed
`((((((…))))))` raises `RecursionError`, and a crash inside a validator is a crash where a refusal
belongs.

`test_it_never_evals` reads the module's own AST: no bare call to `eval`/`exec`/`compile`, no
qualified call ending in `literal_eval`, and `ast` not even imported. The first version of that
test was wrong in an instructive way — it flagged `re.compile`, because an unqualified name check
cannot tell `re.compile` from `compile`. A test that cannot tell them apart is a test that gets
relaxed the first time it fires, so it now checks qualified names.

A hypothesis property test covers the rest: over arbitrary text, `evaluate` returns a bool or
raises `PipelineError` — never `IndexError`, never `RecursionError`, and it does not hang.

## Left for later, deliberately

* **`{{ steps.<id>.<field> }}`.** Refused in v1 because a value that exists only once the run has
  started cannot be shown on the card that authorises the run. If a real pipeline needs it, the
  honest answer is §1's litmus: it wants to be a script, and `dev.execute` runs that script as one
  step.
* **Artifacts are a manifest, not a copy.** `{step, capture, as, pointer}` at the blob the tool
  already wrote. A second artifact store is a second thing to back up, and a copy destination built
  from an author-controlled label is a traversal surface bought for nothing. The label is validated
  as a label anyway, so it can safely become a filename if a need appears.
* **Scheduled runs** stay post-MVP, and PIPELINES.md §5's rule for them — nothing above T1 while
  nobody is watching — is not yet enforced, because nothing schedules anything. `TO VERIFY` when it
  does: `check(..., max_tier=Tier.T1)` is the hook, and it already exists.
* **A live run of `oracle-selfcheck` on this machine.** It is priced against the real policy by a
  test, but nothing has executed it end to end with a person approving the card — the same kind of
  supervised run Phase 8 left for a human, and for the same reason.
