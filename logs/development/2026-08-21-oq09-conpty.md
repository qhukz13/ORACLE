# OQ-09 — `pywinpty` and ConPTY: the answer was fine, the trap was elsewhere

**Date:** 2026-08-21 · **Question:** [OQ-09](../../docs/OPEN_QUESTIONS.md#oq-09) · **Blocks:** P3-T1 requirement 8

---

## What was being asked

`term.*` needs a pseudoterminal. The question flagged three risks, in order of expected
pain: wheel availability on Python 3.12, ConPTY resize handling, and UTF-8/CP1251
mojibake on a Russian-locale Windows install.

**All three were fine. The one that bit was not on the list.**

## Measured

`pywinpty 3.0.5`, Python 3.12.13, Windows 10 19045, throwaway venv.

| worry | result |
|---|---|
| 3.12 wheel | present, installs in under a second |
| Cyrillic **without** `chcp 65001` | ✅ `Привет мир` round-trips intact |
| Cyrillic **with** `chcp 65001` | ✅ identical |
| resize mid-stream (`set_size(140, 45)`) | ✅ session survives; a 300-line burst arrived complete |
| three concurrent sessions | ✅ isolated; A never saw B's output |
| sequential sessions | ✅ third session works as well as the first |

**Cyrillic needs no code-page dance.** ConPTY normalises its output to UTF-8 regardless
of the legacy console code page, so the mojibake this question existed to worry about
does not arise. The historic cp866/cp1251 problem belongs to the old `winpty` console
API, not to ConPTY.

## The actual finding: writing before the shell is ready is swallowed

Half of the early spike runs came back with **nothing at all** — no banner, no echo, no
error, no exception. The shell was alive; `isalive()` was `True`; the marker simply
never appeared.

The variable was time. Drain for 1.5 s before writing, and the write vanished. Drain for
2.5 s, and it worked. Both, repeatedly, on the same machine:

```
drain 1.5s -> works=False  banner=0 chars   (three sessions in a row)
drain 2.5s -> works=True   banner=23 chars  (three sessions in a row)
```

There is no error anywhere in that failure. From the outside it looks exactly like the
agent ignoring you.

Replacing the sleep with a **measured readiness condition** — wait for first output,
then for a 300 ms gap with none — was **8/8 successful at ~0.33 s**, which is also five
times faster than the sleep that happened to work:

```
session 0: ready in 0.35s works=True     session 4: ready in 0.33s works=True
session 1: ready in 0.33s works=True     session 5: ready in 0.33s works=True
session 2: ready in 0.34s works=True     session 6: ready in 0.33s works=True
session 3: ready in 0.33s works=True     session 7: ready in 0.33s works=True
FAILURES: 0 / 8
```

I did not chase the root cause below that. What is established is the behaviour and the
mitigation; claiming a mechanism I have not proven would be worse than saying so.

### Rule for the codebase

**Readiness of an external process is a measured condition, never a sleep.**

This is the second time the same shape has cost real time here. [OQ-16](../../docs/OPEN_QUESTIONS.md#oq-16)
was the toolhost child that emitted `ready` and then silently stopped reading stdin;
this is a shell that is alive and silently ignoring input. Both look healthy. Both are
invisible until something times out with nothing to point at.

## What was built on the answer

`term.open` / `term.read` / `term.write` / `term.close`, in the **toolhost child** — a
shell belongs inside the Job Object, because HALT must be able to stop a runaway
`npm install`. (`app.launch` is the opposite case and lives in the parent for exactly
the opposite reason: nobody has unsaved work in a spinning install, and everybody has
unsaved work in an editor.)

Three decisions worth recording:

- **A reader thread per session, not read-on-demand.** If nobody drains the
  pseudoconsole, the shell eventually blocks on its own output — and a build that
  stalled because ORACLE was not looking would be indistinguishable from a hung build.
- **ANSI is stripped for the model, kept for the UI.** Every cmd.exe prompt carries
  cursor moves and an OSC title string. Feeding those to a 0.8B model is noise it will
  try to interpret.
- **One line per `term.write`, refused otherwise.** Otherwise a single approval covers a
  script and the confirmation card shows the first line of something much longer.

`term.write` is T2 and confirmed **every time**, with a fresh approval bound to the exact
text. There is a test that approves `echo first-command` and then proves the same
approval will not carry `echo second-command`. That is the whole security story for
terminals: a shell has every privilege the user has and no scope an allowlist can
inspect, so the tool-contract argument does not reach it and a human decides each time.
