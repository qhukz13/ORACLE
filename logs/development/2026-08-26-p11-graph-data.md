# Phase 11, before anything is drawn: what is actually in the link table

**Task:** P11-T1 (planning) · **Date:** 2026-08-26 · **Status:** measured, and it moves the design

ROADMAP's Phase 11 says of the knowledge graph: *"The data layer already exists (`knowledge.db`
documents + embeddings + the `links` table); this phase adds the offline layout pass, the persisted
positions, and the view."* UI.md §11b describes what it draws as *"an interactive map of every
indexed document across the Obsidian vaults, project docs and PDFs"*.

Both sentences are true about the schema and misleading about the data. Ten minutes of SQL against
the live index, before writing any layout code:

## The table exists, and it is one collection's

```
documents  1,414        links  1,176  (all kind='wikilink')
```

| | documents | with any outgoing link |
|---|---:|---:|
| `notes` (the Obsidian vaults) | 166 | **157 — 94.6%** |
| `projects` (the code corpus) | 1,248 | **2 — 0.2%** |

Every linked document is markdown. Nothing else in the corpus wikilinks, because nothing else is
written in Obsidian — code does not contain `[[double brackets]]`, and there is no reason it should.

**So a link-only graph of this corpus is a well-connected 166-node notes map plus 1,248 isolated
dots.** That is not "every indexed document across the vaults, project docs and PDFs". It is the
vault, with the rest of the corpus rendered as dust around it.

## Which inverts what the design treats as optional

UI.md §11b and [OQ-22](../../docs/OPEN_QUESTIONS.md#oq-22) both frame semantic edges as an
enhancement that may be switched off — *"if no threshold reads well, semantic edges ship off and stay
a toggle-nothing — the explicit link graph alone may be the honest product."*

On this corpus that is backwards. The explicit link graph **is** honest, but it is a graph of 12% of
the corpus. For the other 88%, semantic edges are not a nice-to-have that improves readability; they
are the only thing that would make those nodes part of a graph at all.

That does not mean ship them regardless — OQ-22's measurement 3 still has to show they read as
clusters rather than a hairball. It means the *decision* changes shape:

* if semantic edges read well → the graph is the corpus, as designed;
* if they do not → the honest product is **a notes graph**, explicitly scoped and labelled as one,
  not a corpus graph with most of the corpus missing. Shipping "the explicit link graph alone" under
  the §11b description would be a view whose title is a claim its content does not support.

## The edges need a resolver, and it is basename-based

`links` is `(from_document_id, to_path, kind)`. `to_path` is the **raw wikilink text**, not a
resolved id — so the layout pass has to resolve it. How well it can:

| resolution of `to_path` against 1,414 documents | |
|---|---:|
| exact `rel_path` match | **0 — 0.0%** |
| unique basename match (Obsidian semantics) | 1,162 — 98.8% |
| ambiguous basename (2+ candidates) | 11 — 0.9% |
| dangling (no such document) | 3 — 0.3% |

Exact-path matching resolves **nothing**, which is the whole finding: a wikilink is written
`[[Backpropagation]]`, not `[[08 - Neural Networks/Backpropagation.md]]`. A resolver that joins on
`rel_path` would produce an empty graph and look like a bug in the layout.

So: resolve on lowercased basename-without-extension. 98.8% land. The 0.9% ambiguous need a rule —
prefer same-folder, then fail closed to *no edge* rather than guessing, because a wrong edge in a map
whose purpose is "show me the shape of what I know" is worse than a missing one. The 3 dangling
links are real Obsidian dangling links (a note that was renamed or never written) and are worth
surfacing rather than hiding: "neglect" is one of the four questions §11b says the view exists to
answer.

## And it makes the rendering question much easier than ADR-0023 assumed

[ADR-0023](../../docs/DECISIONS.md#adr-0023--the-knowledge-graph-is-simulated-then-frozen-canvas-rendered)
commits to canvas rendering, and OQ-22 measurement 2 asks for an SVG control run *"to keep ADR-0023
honest — if SVG survives at this node count, the canvas complexity is unjustified"*.

At **166 nodes and ~1,162 edges**, SVG is not marginal; it is comfortable. The canvas decision was
sized against the ceiling in the design (10k documents), and the corpus is two orders of magnitude
below it on the only part of it that has edges.

This does not settle it — if semantic edges bring the other 1,248 documents into the graph the node
count goes back up by ~8.5x, and *that* is when canvas earns its place. Which means measurements 2
and 3 are not independent, and the order matters: **decide the edge model first, then measure
rendering against the node count that decision implies.** Measuring canvas-vs-SVG at 166 nodes and
concluding "SVG is fine" would be measuring the wrong graph.

## Caveat on these numbers

Read from the live `D:/ORACLE/data/knowledge.db`, last indexed 2026-08-24 (1,414 documents against
the eval walker's 1,506 — the difference is `parse_error` rows and files added since). The
*proportions* are what matter here and they are not close calls: 94.6% against 0.2% does not turn on
90 documents.

# And the other half of Phase 11 has nothing to draw

The knowledge graph is one of four things Phase 11 promises. The other three — the execution tree
(UI.md §6b), the orbit (§3), the timeline and agent queue (§7, §8) — all render **the supervisor's
own activity**. So, the same question asked of that data:

```
events : 302        span: 2026-08-21 .. 2026-08-26   (5 days)
tasks  : 0 rows     0 distinct roots     0 superseded
```

| event type | count |
|---|---:|
| `agent.state` | 132 |
| `message.delta` | 38 |
| `turn.started` / `turn.finished` | 28 / 27 |
| `tool.started` / `tool.finished` | 9 / 9 |
| `approval.requested` / `approval.resolved` | 4 / 3 |

**The `tasks` table is empty.** Not sparse — empty. Every graph ever run on this machine was run by
a test against a temporary database. UI.md §6b's tree draws *"one root task, its plan, its tasks,
their attempts, and the evidence for each"*, and there has never been one.

[OQ-14](../../docs/OPEN_QUESTIONS.md#oq-14) is the sharpest version of the problem. Its go/no-go is
*"cover every label and it must still be possible to say what ORACLE is doing"*, and ROADMAP defends
scheduling it late by saying *"deciding this after months of real event data is exactly why it is
scheduled late."* There are five days of data, 302 events, and zero supervisor executions. **The
question cannot be answered yet, and building the view in order to answer it gets the dependency
backwards.**

## What this changes about the order

Phase 11 has two halves and they have different prerequisites:

* **The knowledge graph** needs the index, which exists and is measured above. It can start now, and
  OQ-22 is its gate.
* **The execution tree, the orbit, the timeline, the queue** need executions. They have none.

Building the tree against fixtures is possible — the vitest suite already does it — but §6b's and
OQ-14's acceptance criteria are *about a real run*: whether a person can look at it and say what
ORACLE is doing. A synthetic fixture cannot fail that test, which means passing it proves nothing.

So the cheapest unblock is not a design decision, it is **running something**. Two candidates were
already carried in `current_task.md` as "left for a person":

1. **`oracle-selfcheck`** — local, no egress, six steps, four of them T2. One person, one approval
   card, about five minutes, and it produces a real six-task graph with real evidence rows,
   real timings and a real `pipeline.finished` record. This is by far the cheaper of the two and it
   was built yesterday.
2. **The Phase 8 scenario on a real project** — a planner, worktrees, egress to Claude. Richer data
   (it exercises `supersedes` lineage, which nothing else does), but it costs real tokens and real
   approvals.

Neither is something an agent should do unilaterally: both are T2-or-above and (2) sends code off
the machine. They are named here as **Phase 11's prerequisite** rather than as chores, because that
is what the empty table makes them.

## Recommendation, stated so it can be argued with

Split the phase along the line the data draws:

* **P11-T1 — OQ-22, the knowledge-graph measurements.** Unblocked today. Note from the section above
  that measurements 2 and 3 are not independent: settle the edge model first, because it decides the
  node count that the canvas-vs-SVG question is asked at.
* **P11-T2 — the execution tree**, after at least one real run exists. `oracle-selfcheck` is enough
  to start; the Phase 8 scenario is what makes `supersedes` renderable.
* **OQ-14 stays open** until there is something to look at. Answering it against fixtures would be
  answering it against a picture we drew ourselves.
