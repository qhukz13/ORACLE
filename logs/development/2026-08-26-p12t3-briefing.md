## The distinction the design turned on: delta vs current state

The briefing looked like one thing — "events since seq N" — and it is two.

**Delta** is what changed: completed, failed, cancelled. The watermark is the whole point;
without it the briefing shows yesterday forever and becomes the notification a person learns
to skip.

**Current state** is what is true *now*, and it must appear regardless of the watermark:

- **`waiting`** — a task parked on an approval. If this were watermarked, acknowledging a
  briefing could **bury the thing that most needs a person**. That would make the feature
  actively harmful, not merely unhelpful.
- **`in_flight`** — pending, ready or running. This one I got wrong first and a test caught
  it: a `RUNNING` task produced an empty `ProjectBrief` and was filtered out entirely, so a
  briefing during a long run would say *"Nothing ran"*. *"What is running now"* is one of the
  six things the vision gives the screen three to five seconds to answer, and a briefing of
  outcomes alone goes blank exactly when somebody most wants to see something.

The test that caught it was written for something else — a task with no timestamps
contributing zero elapsed — and failed with `IndexError: tuple index out of range` because
there was no project brief at all. Second time today a test found a real gap while asserting
something adjacent.

## Where a watermark lives when it belongs to no project

`projects.briefed_through_seq` gives every project its own pointer. The system section — a
daemon that died, a provider that went unreachable — has no project to hang off, and without a
pointer of its own it would reappear in every briefing forever.

`oracle.db` had nowhere to put a daemon-level scalar. `schema_version` is a table because it is
a *list*; everything else lives on a row that owns it. Migration `0007` adds a `meta(key,
value)` table — one thing to reason about instead of a one-column table per scalar, and
`knowledge.db` already has exactly this shape, so it reads without thinking.

Written into the migration comment, because it is the kind of table that attracts the wrong
contents: **this is not for configuration.** Config lives in `config/*.yaml` where a human
edits it and git records the edit. `meta` is for values the daemon computes about itself.

The same migration adds `ix_events_task`. The briefing asks "which tasks in this project saw
activity after seq N", which joins `events.task_id` to `tasks.id` — and `events` had indexes on
`(session_id, seq)`, `(trace_id)` and `(type, ts)`, none of which helps. It would have been a
full scan of the log on every render. The log is ~400 rows today and will not stay that way.

## A dead daemon can only brief itself if it left a note

*"If ORACLE crashed overnight, that is the first line"* was already in UI.md §7b as the
mitigation for [ADR-0025](../../docs/DECISIONS.md)'s named risk — a background service failing
invisibly at 04:00.

Implementing it exposed that it was not implementable as written. **A crash leaves no trace of
itself.** The log simply stops, and a silent gap is indistinguishable from an idle night. You
cannot infer a death from an absence.

So the fact has to be *established*, not inferred:

- `system.shutdown` on the way out, best-effort, before anything is torn down;
- `system.boot` on the way in, carrying `unclean` — computed by looking at what the last event
  in the log actually *was*. A `system.shutdown` means somebody stopped it. Anything else means
  it died.

Both are **critical** event types: a lost one turns a crash report into silence.

One edge worth stating rather than discovering later: a **first-ever boot is not unclean.**
There was no previous run for the absence of a shutdown to mean anything about, and reporting
one would greet every new install with a phantom crash.

## Rendering is arithmetic, and a test says so

Counts, outcomes, timings and cost are computed over task rows. No model, for two reasons that
compound: the briefing has the tightest latency budget of any surface, and it is the one place
where a fabricated summary would be **a summary of the owner's own work**.

`TestNoModelIsOnThisPath` checks it against the source — the module imports nothing from
`oracle.llm` or `oracle.router`, and `render` is a plain `def` with no `await` in it, so it
cannot do I/O at all. Architectural claims decay the moment one import looks convenient, and
"we could just have the local model summarise this" is a genuinely attractive future edit.

The template stays the permanent fallback even once a local summariser exists, because it is
the version that is always correct.

## Smaller decisions worth their line

**`through_seq` is pinned by the caller.** The endpoint reads the log head once and echoes it
back on acknowledgement. Without that, work arriving while the reader is looking would be
marked seen by an acknowledgement of what they never saw.

**An unknown `project_id` on `ack` is a 404**, not a fallback to acknowledging everything. A
permissive handler there would silently clear the whole briefing on a typo.

**A per-project acknowledgement does not touch the system section.** Dismissing one project's
news is a statement about that project; sweeping up the daemon's own report with it is how a
crash gets lost.

**Archived projects are not briefed.** Archiving is a human saying "not now", and the briefing
is the surface that must respect that most, because it is the one that demands attention.

**Repeated degradations collapse to one line, named.** "1 degradation" tells nobody whether to
act; "Ollama is not reachable" does.

## The regression it caused, and why the test was wrong

`test_message_produces_the_full_event_sequence` failed: it asserted
`types[0] == "session.created"` after connecting with `since_seq=0`.

That had been true only *incidentally* — nothing had ever been written to a fresh log before a
session was created. `system.boot` now is. The assertion was pinning an accident of ordering
while the test's actual subject is the sequence **within a turn**, so it now asserts that:
`session.created` appears, and appears before `turn.started`.

Worth noting beyond the fix: this is a **protocol-visible** change. Any client resuming from
`since_seq=0` sees a different first event than it did yesterday. `docs/API.md` already tells
clients to ignore unknown types; it now also says not to depend on the type at a given index,
because this is the first change that makes that rule bite.
