# P8-T3 — the ladder, and two things that were true on paper only

**Date:** 2026-08-25 · **Task:** P8-T3 (fallback ladder, reference scenario, audited override,
REPORT routing) · **Docs corrected:** [PLANNER.md §6](../../docs/PLANNER.md#6-fallbacks),
[PLANNER.md §8](../../docs/PLANNER.md), [UI.md §9](../../docs/UI.md#9-confirmation-center--built-2026-08-21)

Building the ladder was the small half of this task. The large half was finding two claims the
project had been making for a phase and a half that were true of the *payload* and false of the
*system*. Both are recorded here because both were invisible to every test that existed.

---

## 1. The graph card was never rendered

P8-T1's report says: "The graph card — every task with its role, its agent, and whether it will
egress." That is a true statement about `approval.requested`'s preview. The desktop UI matched on
`tool === "ai.delegate"` for the egress box and fell through to the generic EFFECT block for
everything else — and the EFFECT block renders `preview.summary` and `preview.detail`, neither of
which a graph card sets.

So a person approving a twelve-task graph saw the tool name, the tier, and one line of prose. The
task list, the roles, the agents, the "this one egresses" markers and the planner's stated risks
were all on the wire and none of them reached a screen.

P8-T1's own test asserts the injected instruction is *in the preview payload* — "the graph card
**showing** that sentence rather than summarising it away, because approving what you did not read
is the attack". The payload showed it. The card did not exist.

**As built:** `GraphCard.tsx`, rendered for `ai.graph` the way `EgressPreview` is rendered for
`ai.delegate`, with objectives **verbatim** and a vitest that plants the injection string and
asserts it appears character for character. The lesson is not "write more UI tests" — it is that a
security property asserted on a server payload is a property of the payload. The assertion has to
land where the human is.

## 2. A delegation was being handed to the local model

`Registry.holders_of` sorts cheapest first: `free` before `subscription`. `researcher` is held by
both `claude` and `local`, so `_resolve_agent` picked `local` — and the daemon then ran the task
through `make_delegation_runner`, which is the Claude adapter. The row said `agent: local`; the
process was `claude -p`.

Nothing failed, which is why nothing caught it. The row was simply a lie, in the one column that
answers "which agent did this".

**As built:** `resolve_agent()` takes the `TaskKind` and narrows the field before cost order is
consulted — a local model is not a delegation target, and a cloud agent does not hold a REPORT.
Found while doing (3), not by looking for it.

## 3. `REPORT` stops being an admission

P8-T1 shipped `TaskKind.REPORT` mapped to the delegation runner with a comment saying so. The
honest fix was not "special-case the `summarizer` role" but to read the rule off the registry it
was already written in: **a role whose holders are all `locality: local` compiles to `REPORT`**.
`summarizer` is the only such role today; adding another is a YAML edit.

`runners/report.py` summarises from ORACLE's own evidence and **is not shown the workers' claims**
— the same rule as the replan prompt, and for a sharper reason: a local model writing ORACLE's
report from a worker's prose is inter-agent injection one step further from anybody checking.

It degrades to a deterministic listing rather than failing. A report task that failed the graph
because Ollama was not running would report a summary outage as a work outage.

## The ladder itself, and the one rule that makes it safe

Rungs 2–4 are PLANNER.md §6's, built as designed. The decision worth recording is the one that
kept it from becoming a second planning path:

**Every rung produces the same `ExecutionPlan`, checked by the same `validate()`, compiled by the
same `compile_plan()`, shown on the same card at the same tier with the same `external`
provenance.** A template naming a role nobody holds is rejected exactly as a vendor's plan is, and
costs a rung. A plan a person typed meets the same parser — "the author is trusted" is precisely
the control ADR-0021 says never to build, and the person most exposed by a privileged human path
is the person who pastes something they did not read.

Three smaller decisions:

* **A refusal is not a rung.** If the owner declined the planning egress, the ladder stops.
  Descending would be answering "no" with "how about this" — P8-T2's rule, which does not weaken
  because the alternative is cheaper. There is a test, and it also asserts nothing egressed.
* **A template may not name a project.** ORACLE stamps the project it resolved. A template that
  could name one would be a hallucinated path with a YAML file's authority behind it.
* **Substitution is `str.replace`, not `str.format`.** The objective is user text; `format` is a
  small language nobody meant to expose to it. A stray `{` would raise, and `{0.__class__}` is not
  a placeholder anybody designed.

Rung 3 is built in code rather than read from the template file, because the rung below "the
template file is unreadable" cannot itself be in the template file.

## An inconsistency found and deliberately not fixed

`validate()` rejects a task whose role is `verifier` because no agent holds it — correct, and
tested. But `expected_outcome: "verdict"` compiles to a `VERIFY` task *whatever* the role is, so
`reviewer` + `verdict` produces the same deterministically-judged task under a name that implies a
model will judge it. The honest spelling is rejected; the misleading one is accepted.

The narrow fix is to allow a deterministic role when the outcome is `verdict` and reject it
otherwise. It was not made here: it changes plan validation while this task was changing plan
*compilation*, and two changes to the same function in one task is how a regression gets
attributed to the wrong one. The shipped templates use `reviewer` + `verdict`, with a comment
saying why. Worth doing in the task that next touches `validate()`.

## The reference scenario: what a chain of proven links is worth

Five tests already proved each link of

    objective → planning egress → validation → graph approval → per-task gating → verify → report

and none proved the chain. `tests/test_reference_graph.py` runs it with everything below the
vendor real — real policy, real gate, real approvals, real `DelegationService`, real worktree with
its scrub, real harvest, real scheduler, real store — and asserts the *order*, appended to by the
things that actually do the work rather than by the test narrating itself.

It found nothing. That is the correct outcome and it is not an argument against having written it:
the value is that every future change to any seam in Phase 8 now has to keep the order intact, and
"a chain of proven links" is exactly the shape of system that turns out not to work end to end.

Two variants run beside it, because the ladder's whole claim is about paths nobody usually walks:
the same chain on a **template** with no planner reachable, and on the **single-task** rung with no
templates either. Both still ask both questions, in the same order.

## Not done: the supervised live run

Phase 8's last acceptance criterion is one supervised live run of the full scenario on a real
project, both vendors, every preview human-approved. It is not done and was not attempted.

It is not something an agent should do unilaterally: it spends real quota against a real vendor
and its entire point is that a **person** reads each preview and decides. Running it with the
approvals answered programmatically would produce a green tick for the one criterion whose subject
is the human in the loop.

What it should record when somebody runs it: tokens and wall-clock per planning call, per
delegation and per graph; whether the planner's plan for a real objective was worth the two
approvals it cost; and whether the graph card is readable at twelve tasks, which is the number the
size cap allows and a number nobody has looked at on a screen.
