# OQ-18, part 2: the corpus was measured with the wrong chunker, and the cap was never enforced

**Date:** 2026-08-26 · **Task:** P9-T2 · **Follows:**
[the 2026-08-25 truncation measurement](2026-08-25-oq18-truncation.md)
**Scripts:** `scripts/measure_truncation.py`, `scripts/eval_embeddings.py`

P9-T1 measured truncation and concluded that lever 2 of [OQ-18](../../docs/OPEN_QUESTIONS.md#oq-18)
was not the cause of the recall gap. The conclusion survives. **Two of the numbers behind it did
not**, and the reason is worth more than the numbers were.

---

## 1. The measurement was of a chunker the index does not run

`scripts/eval_embeddings.py` carries **its own copy** of the chunker. That was a deliberate and
correct decision for OQ-02: five embedding candidates had to see byte-identical chunks, and
depending on `src/` would have made the comparison depend on whatever the index happened to be
doing that week.

It stopped being correct the moment the model was chosen. On the same corpus:

| chunker | chunks |
|---|---|
| `eval_embeddings.py`'s copy | 12,770 |
| `oracle.rag.chunking` (shipped) | 11,727 |

**8% apart.** Every number either produces describes only itself — including OQ-18's 61%/44%
baseline, which was computed over chunks ORACLE does not produce.

P9-T1's truncation measurement used the copy, so it inherited the same problem. Corrected, with the
shipped chunker and the honest denominator (see §2):

| | P9-T1 said | actually |
|---|---|---|
| embedded chunks over 512 tokens | 20.1% | **27.1%** |
| corpus tokens never embedded | 10.1% | **6.42%** |
| RU fixture files with a truncated chunk | 5 of 25 | **11 of 25** |

Both directions moved, which is what a wrong instrument looks like: it was not biased, it was
measuring something else.

**Fixed by deletion, not by discipline.** `eval_embeddings.chunk_doc` now calls
`oracle.rag.chunking.chunk_document`; the local copy is kept as `chunk_doc_legacy` so pre-2026-08-25
`--models` runs stay reproducible, and nothing calls it. `measure_truncation.py` uses the shipped
chunker too and prints the difference rather than hiding it.

## 2. Config chunks were counted, and they are never embedded

`ContentKind.CONFIG` is indexed lexically and **not** semantically — `indexer.py` reads
`if embedder is not None and doc.semantic`. So a truncated `tsconfig.json` chunk costs BM25 nothing
and the embedder nothing: it was never going to be a vector.

P9-T1 reported one rate over all chunks, which made config's 88% overflow read as a retrieval
problem. It is not one. Both rates are printed now, and the *embedded* rate is the headline.

## 3. The cap was never enforced

The larger of the two defects, and the one that had nothing to do with tokenizers.

`MAX_CHARS` was documented as the ceiling on a chunk. It was applied to the **body**:

* `_pack` accumulated `len(body) + 2` per block while emitting
  `header + "\n\n".join(anchor + "\n" + body)` — the header once and an anchor line per block, none
  of it counted;
* `_window` accumulated line lengths while emitting `prefix + "\n".join(lines)`, with `prefix`
  uncounted;
* the overlap-retention path recomputed `size` as `sum(len(x) for x in buf)`, dropping the newline
  the join would add per line.

On the real corpus the longest "1,800-character" chunk was **4,055 characters**, and 27% of chunks
were over the cap. The unit test that should have caught it asserted `<= MAX_CHARS * 2` — a
factor-of-two tolerance, which is not a budget. That slack is now gone and the assertions are exact.

## 4. 3.6 chars/token is not this corpus

The old cap was justified as "~500 tokens of English prose" at ~3.6 characters per token. Measured
with `bge-m3`'s own tokenizer over the shipped chunks:

| kind | chars/token p1 | p5 | median | chunks |
|---|---|---|---|---|
| code | 2.34 | 2.53 | **3.05** | 7,463 |
| markdown | 2.42 | 2.64 | **3.33** | 3,248 |
| text | 1.67 | 1.75 | **1.93** | 99 |

At the 1st percentile of density, 512 tokens is reached at ~1,200 characters, not 1,800. `text` — a
handful of Russian-heavy files — is denser still, at ~850.

**`MAX_CHARS` is now 1200**, and it stays a *character* cap rather than becoming a token cap. A
token cap would make chunking depend on the tokenizer, which is exactly the coupling that let the
harness and the index drift apart in §1. A character cap calibrated by measurement keeps one
chunker for tests, the indexer and the harness, at the cost of needing recalibration if the model
changes — which `CHUNKER_VERSION` now makes visible.

### Result

| | before | after |
|---|---|---|
| embedded chunks over 512 tokens | 2,925 / 10,808 (**27.1%**) | 101 / 15,498 (**0.7%**) |
| embedded tokens never seen | 6.42% | **0.10%** |
| chunks over `MAX_CHARS` | 27.0%, longest 4,055 chars | 3.0%, longest 1,346 chars |
| chunks (embedded) | 10,808 | 15,498 (**+43%**) |

The residual 3.0% over `MAX_CHARS` is config and plain text, where a single unsplittable line
exceeds the room left after the prefix. Config is not embedded; text is 154 chunks. The residual
0.7% over the token window is 101 chunks with a mean overshoot of 47 tokens.

**+43% more chunks is the cost**, paid in index size and indexing time. Whether it buys recall is
§5, and it is the only reason to do it.

## 5. An index can now tell it was cut by a different chunker

`KnowledgeStore.bind` already refuses an index built by a different embedding model, because
"an index built by one model and queried by another does not fail — it returns confident nonsense".
A boundary change is the same class of problem and had no such guard: incremental indexing does not
rebuild rows it already has, so moving a boundary leaves a database half cut one way and half the
other, with nothing failing and retrieval quietly getting worse.

`CHUNKER_VERSION` is recorded beside the model and checked the same way. It surfaces through the
paths that already exist — the health view reports "not stale, wrong", the watcher reports it and
stops rather than triggering a surprise full reindex.

## 6. The summary table was off by one

Found while reading the baseline: `eval_embeddings.py` printed a header naming four
percentage columns and a row containing five. `RU@5` sat under `rrf_w2`, and every reader
of that table — including whoever recorded OQ-18's original numbers — was reading one
column to the left of what they thought.

Fixed, with the widths taken from the row field by field. Worth its own paragraph because
it is the third instrument bug in two days (the chunker copy, the config denominator, this),
and they share a shape: **the measurement was fine and the presentation of it was not.**

## 7. Recall

### Baseline `2026-08-26, shipped chunker, MAX_CHARS=1800`

`logs/measurements/oq18-before.json`. 10,810 embedded chunks, 8,032 s of CPU at 1.3
chunks/s.

| fusion | recall@5 |
|---|---|
| BM25 alone | 29% |
| dense alone | 63% |
| `rrf` | 58% |
| **`rrf_w2`** | **68%** |
| `gated` | 58% |
| **RU (crosslang) @5** | **40%** |

Two things to say about this before the comparison, because both change what OQ-18's
recorded numbers mean:

* **The overall best is 68%, not 61%.** OQ-18 recorded 61% for the fixed fusion gate. On
  the shipped chunker the *gated* strategy scores 58% and `rrf_w2` scores 68%. The
  difference is the chunker swap of §1: the old number described the harness's copy.
* **RU is 40%, not 44%**, for the same reason and in the other direction.

Neither is a regression. They are the first numbers this project has that describe the
code it ships.

### After `2026-08-26, MAX_CHARS=1200 enforced`

`logs/measurements/oq18-after.json`. 15,521 embedded chunks, 7,523 s of CPU at 2.1
chunks/s — **faster in wall-clock than the baseline despite 43% more chunks**, because
attention cost is superlinear in sequence length and these sequences are shorter. The
index grew from 44 MB to 64 MB.

| strategy | before overall | before RU | after overall | after RU |
|---|---|---|---|---|
| BM25 alone | 28.9% | **0.0%** | 28.9% | **0.0%** |
| dense alone | 63.2% | 56.0% | 65.8% | 60.0% |
| `rrf` (dense + BM25) | 57.9% | 40.0% | 63.2% | 48.0% |
| `rrf_w2` (BM25 down-weighted) | 68.4% | 56.0% | 71.1% | 60.0% |
| `dense_xl` (dense + English probe) | — | — | **73.7%** | **72.0%** |
| `rrf_xl` (that, plus BM25) | — | — | 65.8% | 52.0% |

**The chunker repair works.** Every strategy improves: +2.6 to +5.3 points overall and
+4 to +8 on the Russian subset. Nothing regressed, and indexing got cheaper.

**The English probe is the largest single lever measured**: dense 65.8 → 73.7 overall
(+7.9) and 60.0 → 72.0 on the cases it exists for (+12.0). These are *human* translations
— the ceiling of the idea, not the router model's Russian (see the fixture header).

## 8. The third lever, which OQ-18 did not name

Read the BM25 row: **0.0% on Russian, in both runs.** Now read what fusing it costs:

| | dense | + BM25 | cost |
|---|---|---|---|
| RU, before | 56.0% | 40.0% | **−16.0** |
| RU, after | 60.0% | 48.0% | **−12.0** |
| RU, after, with the English probe | 72.0% | 52.0% | **−20.0** |

A Russian query has no lexical purchase on a Latin corpus, so BM25 returns fifty ranked
results of noise and unweighted RRF admits them as a second opinion of equal standing.
They do not fail to help; they displace correct dense hits out of the top 5.

**This is not news to the shipped code, and that is the finding.** `retrieval.py`'s
`discriminating_terms` already drops minority-script terms *at any frequency* — measured
2026-08-24 at exactly the 12 points this run reproduces — so a Russian query returns no
lexical terms, `retrieve()` skips the lexical half, and ORACLE takes the **dense-only**
path.

`eval_embeddings.py`'s `gated` strategy uses `BM25.answerable()`, which has **no script
rule**. It is not the shipped gate. So `rrf` and `gated` in the table above describe a
fusion ORACLE does not perform for these queries — the fourth instrument discrepancy in
three days, and the one with the largest consequence:

> **OQ-18's "44% on the 25 Russian fixtures" was measuring a code path that does not run.**

### What ORACLE actually scores

Composed per-case from the miss lists — dense for a query the script rule gates, `rrf`
otherwise, which is exactly what `retrieve()` does:

| | overall | RU |
|---|---|---|
| shipped, before this task | 68.4% | 56.0% |
| **shipped, after the chunker repair** | **71.1%** | **60.0%** |
| shipped + the English probe | **78.9%** | **72.0%** |
| the gate | 80% (31 of 38) | — |

**78.9% is 30 of 38. The gate needs 31. One case.**

The eight still missing with everything applied: `en-relay-dockerfile`, `ru-air-gap`,
`ru-audit-trail`, `ru-cross-validation`, `ru-model-degrades`, `ru-pairing-bruteforce`,
`ru-terminal-reattach`, `ru-workspace-permissions`.

One of them is structural: `en-relay-dockerfile` expects `Asterim/Dockerfile.relay`, a
**config** file, which is indexed lexically and never embedded — no dense probe of any
quality can retrieve it, and the lexical half is what should. It is a fixture that tests
the fusion the script rule turns off.

## 9. Where that leaves the gate

Both levers OQ-18 named are now measured, and a third it did not name is measured too:

| lever | effect on the shipped path |
|---|---|
| 2 · truncation (fixed) | +2.7 overall, +4.0 RU |
| 1 · query translation (ceiling) | +7.8 overall, +12.0 RU |
| 3 · lexical fusion on crosslingual queries | already correct in `retrieval.py`; the *harness* had it wrong |

68.4% → 78.9%, **+10.5 points**, and one fixture short of 80%.

**The gate is not moved.** 6.3 points on 38 fixtures is 2.4 cases, and a gate re-argued to
sit just below where the numbers landed would be a gate that measures nothing. What has
changed is that "unmet" now has a number, a decomposition and a named next step instead of
two untested hypotheses.

**What is not shipped, and why.** The translation mechanism is not implemented. Two things
are missing and neither is a matter of typing:

1. **The translator's quality is unmeasured.** +12.0 RU is what a *human* translation buys.
   Whether a resident 0.8B model's Russian reaches it is a separate question, and shipping
   on a ceiling measurement is how a system acquires a feature that works in the log and
   not on the machine. Ollama was not running here, so it could not be answered.
2. **The latency does not fit the interactive path.** The second probe alone costs one more
   query embedding — 63 ms p50, 97 ms p95 measured in this run — against a budget OQ-18
   records as having ~70 ms of headroom, before the generation call that produces the
   translation. Where it *does* fit is the Handoff Packet, where a delegation takes minutes
   and retrieval already runs.

## Reproducing

```
uv run python scripts/measure_truncation.py --json out.json
uv run python scripts/eval_embeddings.py --models bge-m3 --out logs/measurements/run.json
```

The first costs about a minute and needs only the tokenizer. The second embeds the whole corpus on
CPU at ~1.3 chunks/s — about two and a half hours — and needs the ONNX model. Neither is in
`scripts/check.py`: both need the real corpus and the models on disk, and a gate that cannot run on
a fresh checkout is not a gate.
