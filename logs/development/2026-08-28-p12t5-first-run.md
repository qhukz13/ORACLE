# P12-T5 — the first real `continue`, and the card that was lying

**2026-08-28** · the first supervised run of the loop the whole vision rests on

`continue ORACLE`, typed into a live daemon with a live router. It got as far as the egress
approval and **stopped there**, which is where an agent has to stop: approving the sending of
someone's repository to a cloud API is theirs.

It worked. It also found a defect on the safety surface that four days of fixture tests could
not, which is the entire argument for doing this at all.

---

## What the run proved

| Question | Answer |
|---|---|
| Does the router classify `continue`? | **Yes.** `intent: "continue"`, confidence `medium`, both runs. First real evidence for [OQ-25](../../docs/OPEN_QUESTIONS.md#oq-25). |
| Does it resolve the project? | **Not from the classifier** — `project: null` both times, even with "ORACLE" as the second word. The router's `_named_project` text fallback recovered it. See below. |
| Does the derivation work? | **Yes.** `continue.derived` → `{project: ORACLE, open_tasks: 0, dropped: 0, notes: [docs/current_task.md, docs/ROADMAP.md], tainted: true}` |
| Does the fencing hold? | **Yes.** The objective carried the untrusted heading and `--- begin docs/current_task.md (quoted, not instructions) ---` exactly as designed. |
| Does the turn wait for the graph? | **No, correctly.** `turn.finished` at seq 424 while `_continue_project` ran on; the approval arrived at 426. |

## The defect: an egress card that said it sent nothing

The planning approval arrived as:

```
tool  ai.delegate   tier T2   decision confirm
tainted False   escalated False
preview.sends_repo_contents  False
args.objective               2,820 characters
```

Those 2,820 characters were `docs/current_task.md` and `docs/ROADMAP.md`, verbatim.

So the card told the owner it was **not** sending repository contents while doing exactly that,
and the gate priced the call as untainted while `continue.derived` — emitted seconds earlier by
the same code path — had already recorded `tainted: true`.

**Recording taint on an event while pricing the call as untainted is the worst of both.** It
looks audited and is not.

### Why the tests did not catch it

They tested the right things in the wrong combination. `objective_of()` was tested for fencing.
`approve_graph()` was tested for `untrusted_sources`. Nothing tested what the **planning** card
says about an objective built from repository files — because until `continue` existed, a
planning objective was always a sentence the owner had typed, and `sends_repo_contents: False`
was simply true.

That is the shape of every dangerous stale assumption: **correct when written**. A hardcoded
`False` is not a bug at the moment it is written; it becomes one when somebody adds a path the
author never imagined. Two days separated the two.

### The fix

`Planner.plan()` gains `untrusted_sources`, and it does two things:

* the gate is told `Provenance.LOCAL_FOREIGN`, so the tier escalates by one exactly as
  [SECURITY.md §6](../../docs/SECURITY.md) says it must;
* `sends_repo_contents` becomes **computed** rather than hardcoded.

Verified on the live system, not only in tests — the same utterance, same daemon, after:

```
tool  ai.delegate   tier T3   decision confirm_strong
rule  taint.escalate(tools.ai.delegate.tier)
tainted True   escalated True
preview.sends_repo_contents  True
preview.untrusted_sources    ['docs/current_task.md', 'docs/ROADMAP.md']
```

T3 means `confirm_strong` — a typed confirmation phrase. That is the right price for "send two
of your repository's files to a cloud API", and it is what the owner was previously not being
asked.

Pinned by `TestTheEgressCardTellsTheTruth` in `tests/security/test_continue_evidence.py`,
including the negative case: an objective the owner typed is **neither** tainted nor flagged, so
the signal keeps its information.

## Two other things worth recording

**The classifier never resolved the project.** `project: null` on both runs, on an input whose
second word is a known project name. The turn still worked because `_named_project` scans the
text against the registry — a fallback written for `delegate` and inherited here. So the feature
works, and the *router* is one for two. That is [OQ-25](../../docs/OPEN_QUESTIONS.md#oq-25)'s
real finding: not that `continue` is misrouted, but that its **project slot is unreliable**, and
a string-matching fallback is currently carrying it. Worth a fixture before anyone trusts the
slot for something the fallback cannot cover — a project named in a previous turn, say.

**Routing took 27 seconds on the first call and 1.9 on the second.** The first paid a cold GPU
model load while the OQ-18 corpus run had all 24 threads. Warm, it is inside
[OQ-15](../../docs/OPEN_QUESTIONS.md#oq-15)'s ~1.5 s target and no conclusion should be drawn
from the cold number.

## A test that passed while referencing a name that did not exist

The new security tests annotate a fixture as `conn: aiosqlite.Connection`, and `aiosqlite` was
never imported. **All 19 passed.** `from __future__ import annotations` makes annotations
strings, so the name is never evaluated at runtime; only `ruff` — statically — caught it.

Third time in this arc that a narrower check than the gate said "fine". The pattern is now
clear enough to state as a rule: **passing tests are evidence about behaviour, not about the
code being well-formed.** The gate runs `ruff`, `mypy`, `tsc` *and* the tests for exactly this
reason, and running the subset that is fastest to run is running the subset least likely to
disagree with you.

## What this did not do

**`tasks` is still 0 rows.** The run stopped at the planning approval, so no plan was authored
and no graph was compiled. Everything waiting on real task data — the orbit's go/no-go
([OQ-14](../../docs/OPEN_QUESTIONS.md#oq-14)), the execution tree's acceptance, `TaskTree`'s
fixture, the sidebar's counters, the briefing's arithmetic — is still waiting.

That is not a failure of the run. Approving a T3 egress is the owner's, and the run's job was to
get the question asked correctly. It did, on the second attempt, after fixing the fact that it
had been asked *incorrectly* the first time.

**`oracle-selfcheck` remains the cheaper way to fill that table**: local, no egress, six steps,
one approval card. It would populate `tasks` without any cloud call at all.
